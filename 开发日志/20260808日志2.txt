  Clarifying Connection Issues
  经过深入排查 GitHub Actions 的报错日志，我已经定位到了 update_stock_basic.py
  执行失败的底层物理原因，并完成了代码的修复与验证。
  ──────
  ### 🔍 报错根因分析 (Root Cause Analysis)

  1. Baostock 漫长拉取导致数据库连接陈旧假死 (Stale DB Connection)：
  脚本在初始化时建立了数据库连接 conn，随后调用 fetch_all_stock_basic() 向 Baostock 请求全量 8,885 条
  证券资料（包含股票、指数、ETF等）。在漫长的跨网拉取过程中，conn
  没有进行心跳保活，连接在写入前已经处于被边缘网关断开或假死的边缘。
  2. 单条 SQL 报文过大引发连接强行断开 (Unbatched Giant Executemany)：
  在原有的 sync_stock_basic 函数中，直接将 8,885 条记录全量传入 cur.executemany。PyMySQL 尝试在单条 Socket
  通信中打包发送包含 60,000+ 参数的超大 Query。这超出了 TiDB Cloud 边缘网关的单次 Query 报文与耗时限制，导致 MySQL
  服务端直接关闭了底层 TCP 套接字，抛出 pymysql.err.OperationalError: (2013, 'Lost connection to MySQL server during
  query')。
  3. 异常处理触发二次报错 (Secondary Failure on Closed Connection)：
  当连接被服务器关闭后，except 块中调用 conn.rollback() 尝试向已经死亡的连接发送 ROLLBACK 命令，因而抛出了 pymysql.err.
  InterfaceError: (0, '') 掩盖了最深层的连接丢失原因。
  ──────
  ### 🛠️ 实施的修复方案

  1. 全量同步改造为 500 条/批次切片写入 (Chunked Batch Insert)：
  在 update_stock_basic.py 与 update_stock_industry.py 中，将 sync 函数改造为 batch_size=500 的分批循环写入，大幅平滑单次
  SQL 报文大小与数据库压力。
  2. 数据写入前心跳保活与自动重连 (Connection Keep-Alive)：
      • 在 __init__.py 和 db_config.py 中统一导出 ensure_connection_alive。
      • 在每个批次写入前自动执行 conn = ensure_connection_alive(conn)，确保连接即使在长时拉取后也能无感自动恢复。
  3. 安全异常回滚 (Safe Rollback)：
  给 conn.rollback() 和 conn.close() 加上安全的 try...except 容错处理，防止连接死亡后引发二次报错。

  ### 🔍 现象背后的 4 步连锁反应分析

  #### 1. 为什么走的是 Render 本地后台线程，而不是 GitHub Actions？

  从日志中的这行提示可以看出来：

  │ [Engine Hub] 算力引擎: 后台计算线程

  由于当前 Render 的环境变量中未配置 GH_PAT (GitHub Personal Access Token)，系统无法向 GitHub API
  发起调度，因此自动回退（Fallback）到了在 Render 容器的 Flask 内部启动 Python 后台守护线程 (threading.Thread) 来计算。

  #### 2. 第 18 秒发生了什么？（Worker 被杀与 HTML 报错）

  日志中出现了极关键的一行：

  │ [Progress 18s] ⚠️ 轮询状态探针检测中: Unexpected token '<', "<!DOCTYPE "... is not valid JSON

  • 发生在 18 秒的这行报错，是 Render 容器或者 Gunicorn Worker 因为内存峰值或执行超时触发了系统强制重启。
  • 在重启的那 1~2 秒内，网页发给 Render 的请求拿到了 Render 网关返回的 502 Bad Gateway HTML 报错页（即 <!DOCTYPE html...
  ），因此前端 JavaScript JSON 解析抛出了 Unexpected token '<'。

  #### 3. 为什么数据库状态会永远卡在 running？

  • 当 Render 的 Worker 被操作系统强行杀死（SIGKILL）时，Python 解释器瞬间被销毁，根本无法触发 try...except...finally
  代码块。
  • 结果：TiDB 数据库 update_progress 表里的这条任务记录状态被永久冻结在了 status = 'running'，无法被写入 failed 或
  success。

  #### 4. 为什么前端会一直轮询到 1335 秒（20多分钟）？

  • Worker 重启恢复后，Render Web 服务恢复响应。
  • 前端网页探针每 3 秒去查询一次数据库中的状态，查到的始终是第 3 步里遗留的 status = 'running'。
  • 前端代码以为后台依然在“正常计算”，因此计数器一路累加打印 [Progress 1335s]。
  ──────

      • 配置后，网页点击【运行】时将直接把重度选股计算分派给 GitHub Actions 的 7GB 大内存虚拟机，彻底摆脱 Render

  3. 前端增加单次轮询上限保护

  ### 真实情况解析：为什么之前改了，网页点击还会跑在 Render 上？

  在我们的系统架构中，实际上有 两种完全不同的策略运行触发场景：

  #### 场景 1：每天 18:31 自动盘后运行（每日定时任务）

  • 运行地点：100% 在 GitHub Actions（7GB 虚拟机）中运行。
  • 是否依赖 Render：完全不依赖！ 哪怕您把 Render 网站关掉、电脑关机，每天 18:31 GitHub
  也会准时在离线算力引擎里跑完全量选股，存入数据库并把精选结果发到您的邮箱。
  • 当前状态：这个工作流已经在 GitHub 上完美配置好了。

  #### 场景 2：在 Render 网页上手动点击【策略运行】（网页在线实时重算）

  • 触发过程：当您在网页控制台上手动点击【开始策略运行】时，请求是发给 Render 网页服务器的。
  • Render 的逻辑：Render 收到您的点击后，需要向 GitHub 的官方接口（https://api.github.
  com/repos/wxsw3000/ashare/dispatches）发一条 HTTP 指令，告诉 GitHub：“请给我在 Actions 离线算力里跑一次选股！”
  • 为什么之前它没有在 GitHub 上跑，而是回退到了 Render？
      • 因为 Render 容器调用 GitHub 接口时，必须持有您 GitHub 账号的“操作钥匙”——即 GH_PAT (GitHub 个人访问令牌)。
      • 由于目前 Render 云平台的环境变量中还没有填入 GH_PAT，Render 服务发往 GitHub 的请求因鉴权失败被打回，Render
      只好打出一行日志：⚠️ 触发 GitHub Actions 异常，回退至本地后台线程，被迫在资源极小的 Render
      本地容器里开了一个后台线程，结果被 Render 的 512MB 内存机制给杀掉了。
