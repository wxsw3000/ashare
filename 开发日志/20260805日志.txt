  ### 📌 根本原因分析 (Why OOM Occurred)

  1. Render 免费实例的内存硬限制 (512MB RAM)：
  Render 的 Free Web Service 实例只有 512MB 内存。一旦运行中的 Python 进程占用的内存突破 512MB，Render 就会自动发送
  SIGKILL 强制终止并重启容器。
  2. 全市场数据在内存中载入 (db.py)：
      • 当在前端在线触发 股票策略回测（/api/backtest）或 策略实时扫描（/api/strategies/<id>/run）时，后端会调用
      load_all_data_db() 和 load_roe_data_db()。

      字典（all_data[code]），峰值内存会短时间内飙升至 600MB ~ 1GB，必然触发 Render 512MB 限制。
  3. Web API 与计算密集型任务共用进程 (server.py)：
  Render 上的 Flask/Gunicorn 在收到回测请求时在同一 Worker
  进程中即时计算，大数据集无法及时被垃圾回收（GC），直接引发崩溃重启。

  以内），主要有以下 4 种架构层面的优化思路：
  ──────
  ### 💡 思路一：股票池“分批流式计算” (Batch / Chunked Processing) — 【最推荐，收益最高】

  • 核心原理：
  我们之所以会内存超限，是因为一次性把全市场 5,000 支股票 1~2 年的 K 线和财报全部塞进了内存。
  我们可以把 5,000 支股票拆分成 10 个批次（每批约 500 支股票） 或 20 个批次（每批 250 支股票）。
  • 执行流程：
      1. 第 1 批 (1~500 股)：加载数据 ➔ 计算这 500 股的买卖信号 ➔ 暂存信号 ➔ 清空内存 (del + gc.collect())。
      2. 第 2 批 (501~1000 股)：加载数据 ➔ 计算信号 ➔ 暂存信号 ➔ 清空内存。
      3. 依次循环 10 次，处理完全市场 5,000 支股票。
      4. 最后将 10 个批次的买卖信号按日期汇总，进行账户资金撮合与收益率计算。
  • 内存效果：内存中同一时刻永远只存在 500 支股票，数据内存峰值直接暴降 90%（从原本的 500MB+ 降至 40MB~80MB），Render
  的 512MB 限制将再也无法触发。
  ──────
  ### 💡 思路二：数据库 SQL 端粗筛 (Database-Side Filtering) — 【效率最高】

  • 核心原理：
  目前很多策略的初筛条件（例如：PE > 0 且 PE < 35、ROE > 5%、资产负债率 < 70%），是在 Python
  中把全市场数据拉下来后再进行 Pandas 过滤的。
  • 执行流程：
  把基本面/估值条件的初筛交给 TiDB 云数据库来做（利用 SQL WHERE 条件和索引）。
  例如原本 5,000 支股票，经过数据库几毫秒的过滤后，真正符合条件的股票可能只有 500~800 支。Python 只需拉取这 800
  支有希望选中的股票 K 线即可。
  • 内存效果：减少 80% 以上无用数据的传输与内存占用。
  ──────
  ### 💡 思路三：滑动窗口历史切割 (Sliding Window Truncation)

  • 核心原理：
  如果回测只需要计算 20 日均线 (MA20) 和 60 日均线，我们并不需要把过去 2~3 年的完完整整 1,000 天 K
  线全部保留在内存字典中。
  • 执行流程：
  数据拉取时只保留回测起始日前 N 天（如 60 天预热期）到结束日的数据，裁剪掉更久远的历史沉积数据。
  ──────
  ### 💡 思路四：数据结构极致轻量化 (Python Data Type Optimization)

  • 核心原理：
  Python 的字符串（如股票代码 'sh.600000'）和 dict 字典结构有相当大的内存 Header 开销。
  • 执行流程：
  把股票代码字段转为 Pandas 的 Category 类型，并剔除掉计算用不到的字段（如 open, high, low 等只保留 close 和
  volume），进一步减少 30% 内存。
  ──────
  ### 总结与方案建议

  如果想要 “既要 5000 股全计算，又要内存绝对不超标”：
  “思路一（分批流式计算）” 是最稳妥、最干净利落的解法。它可以确保内存峰值被硬性死死锁定在 100MB
  踩线以下，且代码改动清晰可控。
