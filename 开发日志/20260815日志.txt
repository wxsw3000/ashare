    import sys
    import os
    # 导入 MagicSTG 核心模块
    sys.path.insert(0, os.path.abspath("."))

    from MagicSTG.core.db import load_all_data_db, get_connection
    import pandas as pd

    # 1. 直接从 TiDB Cloud 加载数据 (示例拉取 2024年至今的数据)
    print("正在从 TiDB Cloud 拉取数据...")
    klines = load_all_data_db(start_date="2024-01-01", limit_to_csi300=True) # limit_to_csi300=True 可用于加速开发测试

    # 2. 编写你的自定义选股逻辑
    selected_stocks = []
    for code, df in klines.items():
        if len(df) < 20:
            continue
        # 示例规则：收盘价突破 20 日均线且 PE(TTM) < 30
        df['ma20'] = df['close'].rolling(20).mean()
        latest = df.iloc[-1]
        if latest['close'] > latest['ma20'] and 0 < latest.get('peTTM', 999) < 30:
            selected_stocks.append((code, latest['close'], latest.get('peTTM')))

    print(f"筛选出的股票 (共 {len(selected_stocks)} 只):")
    for stock in selected_stocks[:10]:
        print(stock)

  index_kline_day 存储的是**“官方统计的大盘指数/行业指数行情数据”**（比如：上证指数 sh.000001、深证成指 sz.399001、沪深300指数 sh.000300、创业板指 sz.399006 等）。

  • 性质：它是一个纯统计指标/抽象数值，表示整个市场或某个板块的总体价格变动趋势（比如今天上证指数是 3000 点）。

  • 我们在系统中的作用：主要用于大盘择时过滤（Market Filter）。比如在多因子策略中设置 enable_market_trend: true 时，系统会去查 index_kline_day 里的沪深300指数，只有当大盘站在 250 日均线上方（牛市/安全环境）时，才允许买入个股。
  ──────
  ### 2. ETF 基金又是什么？

  ETF 是在交易所上市交易的“基金”（比如：沪深300ETF 510300、创业板ETF 159915、芯片ETF 159801 等）。

  • 性质：它是基金公司为了“追踪指数”而发行的真实金融产品。
  • 可交易性：ETF 像股票一样可以直接实时买卖交易（有独立的买卖挂单、成交量、佣金，每份价格比如 3.5 元）。
  • 与指数的关系：ETF 是锚定/复制指数的。比如你买入 1000 份 沪深300ETF (510300)，收益率就几乎完全等同于 沪深300指数 (sh.000300) 的涨跌。

> 那为什么 我们的 index_kline_day中 会有 open high low close等字段呢？

  这个问题问得非常到位！很多刚接触金融数据的开发者都会有这个疑惑：既然指数不能买卖，为什么指数也会有“开盘价 (open)”、“最高价 (high)”、“最低价 (low)”和“收盘价 (close)”呢？

  原因如下：
  ──────
  ### 1. 指数不是静止的，它随交易时间每秒都在实时计算

  指数虽然不能直接买卖，但交易所（上交所、深交所、中证指数公司）会在交易时间内，根据该指数包含的所有成分股的实时成交价格，按照权重实时计算出一个最新的“指数点数”（比如上证指数当前是 3050.25 点）。

  在一天 4 个小时的交易时间里，指数点数是一直在波动的：

  • 开盘价 (open)：每个交易日早上 9:15-9:25 集合竞价结束、9:30 正式开盘瞬间，根据所有成分股开盘价计算出来的指数开盘点数。
  • 最高价 (high)：全天 4 小时交易过程中，计算出的最高指数点数。
  • 最低价 (low)：全天交易过程中，计算出的最低指数点数。
  • 收盘价 (close)：下午 15:00 收盘瞬间，所有成分股收盘后算出的最终收盘点数（通常大家常说的“今天上证指数收在 3000 点”，指的就是 close）。
  ──────
  ### 2. 在量化分析中，指数 K 线的作用

  正因为指数拥有了 open, high, low, close 这些价格数据，量化策略才能像分析股票一样，对大盘指数进行各种技术指标计算：

  1. 计算移动均线 (MA)：通过连续 20 天的收盘点数 close 计算出大盘的 20 日均线 (MA20)，从而判断大盘是在多头趋势还是空头趋势。
  2. 计算振幅与波动率：利用每天的 high 和 low，计算大盘全天的波动幅度。
  3. 计算大盘涨跌幅 (pctChg)：比较今天的 close 和昨天的 close，得出今天大盘涨跌了百分之多少（比如大盘今天暴跌 3%，策略自动触发全线止损或清仓）。
  ──────
  ### 💡 一句话总结

  在金融习惯中，指数的点数（Points）通常直接被映射/记录为 open, high, low, close 的“价格字段”。

  所以 index_kline_day 里的 open, close 代表的是指数当时的点数，而不是能直接用钱购买的商品单价！

> 請你爲我詳細講述DynamicFactorStrategy 的功能

● Read(E:/ashare/MagicSTG/strategies/dynamic_factor.py) (ctrl+o to expand)

  DynamicFactorStrategy（动态多因子选股与信号生成策略）是整个 MagicSTG 系统中最核心、功能最强大且使用最频繁的旗舰策略引擎。

  它的核心理念是：将技术面量化指标、基本面财务指标和大盘择时风控融为一体，通过纯配置化的方式实现高度自由的选股与择时。

  以下是关于它的详细功能与内部工作流程介绍：
  ──────
  ### 1. 核心四大维度功能

  #### ① 技术面指标过滤 (Technical Factors)

  • 均线金叉 (enable_golden_cross)：判断短期均线（默认 5 日 short_ma）是否上穿长期均线（默认 20 日 long_ma）。
  • 成交量放大 (enable_volume_surge)：判断当日成交量是否大于过去 20 日平均成交量的 N 倍（默认 1.2 倍 volume_surge_factor），挑选有资金介入的股票。
  • 动向指标比例 (enable_di_ratio)：计算 DMI 指标中的 +DI 与 -DI 比例（di_ratio = pdi / ndi），衡量多头力量是否强于空头（可设定 buy_di_threshold 阈值，如 0.7）。

  #### ② 基本面财务报表过滤 (Financial Factors)

  • 估值约束 (enable_pe)：设定市盈率 PE(TTM) 范围（如 0 < PE ≤ 30），剔除亏损或估值过高的股票。
  • 盈利能力 ROE (enable_roe)：要求最新季报平均 ROE 大于设定值（如 ≥10%）。
  • 成长性 (enable_growth)：要求净利润同比增长率 YOYNI 大于设定值（如 ≥15%）。
  • 偿债风险防范 (enable_debt_limit)：过滤资产负债率高、财务杠杆过大的公司（如要求资产负债率 ≤60%）。
  • 现金流质量 (enable_cash_quality)：检查经营现金流/净利润比例（CFOToNP），挑选真金白银盈利的公司。

  #### ③ 大盘择时风控 (Market Filter)

  • 大盘趋势看门狗 (enable_market_trend)：在选股前先自动拉取沪深 300 等大盘指数（sh.000300）。
  • 只有当大盘指数站在年线/250日均线上方（多头市场）时，才允许产生买入信号；若大盘处于熊市下行通道，自动全局休克防守，暂停开仓以保护资金。

  #### ④ 多因子综合排序与 Top N 筛选 (Ranking & Selection)

  • 经过上述所有硬性条件筛选后，策略支持对候选股票按指定的因子进行排序：
      • 支持按 PE 升序（低估值优先）、ROE 降序（高盈利优先）、净利润增速降序（高成长优先）或最新股价升序进行二次精选。
      • 最终只截取最优质的前 N 只（top_n，如 5 只）生成买入推荐信号。

  ──────
  ### 2. 性能与数据安全三大黑科技

  #### 1. 严格防范未来数据泄露 (Zero Future-data Bias)

  在加载财务数据时，DynamicFactorStrategy 不使用财报截止日 (stat_date)，而是严格使用实际披露日 (pub_date)。
  在回测历史上任意一天（如 2024 年 4 月 10 日）时，算法通过二分查找 np.searchsorted，确保只获取 4 月 10 日及之前已经依法披露的财报（即使 2024 一季报已出来，只要还没披露就不使用），从根本上保证了回测的真实性。

  #### 2. SQL 跨表查询动态按需跳过

  如果没有开启任何财务因子（如只跑纯均线突破策略），引擎会自动识别并直接跳过 4 张财报大表的数据库查询，使数据加载和回测速度提升 4倍以上。

  #### 3. 智能指标缓存与内存垃圾回收 (_indicator_cache & GC)

  在进行全市场 5000+ 只股票的大跨度历史回测时，对指标矩阵进行矢量化计算（Numpy/Pandas vectorization），并在每批数据处理完后主动调用 gc.collect() 释放内存，确保程序在 Render 512MB 限制的环境下稳定运行。
  ──────
  ### 3. 如何配置使用 DynamicFactorStrategy？

  在代码或 Web 界面中，你只需要准备一个字典/JSON 配置：

    from MagicSTG.strategies.dynamic_factor import DynamicFactorStrategy

> 那麽這套引擎同時支持了股票策略和可轉債策略麽？

● Read(E:/ashare/MagicSTG/strategies/cb_double_low.py) (ctrl+o to expand)

  简洁明确的回答：

  目前系统中，股票策略和可转债策略是由各自专属的策略类分别驱动的，它们共同继承了统一的策略基类 (BaseStrategy)，并共享同一套底层的选股推荐、持仓管理和回测引擎！

  具体架构划分如下：
  ──────
  ### 1. 两套专属策略类（分工明确）

   策略类名称                                                                               │ 适用资产类型                                                                            │ 核心关注指标 / 因子
  ──────────────────────────────────────────────────────────────────────────────────────────┼─────────────────────────────────────────────────────────────────────────────────────────┼──────────────────────────────────────────────────────────────────────────────────────────────
   DynamicFactorStrategy                                                                    │ 股票策略                                                                                │ 均线金叉/死叉、成交量放大、PE(TTM)、ROE、净利润同比增速、资产负债率、现金流质量、大盘择时
   CBDoubleLowStrategy                                                                      │ 可转债策略                                                                              │ 转债现价、转股溢价率 (%)、双低值 (现价 + 溢价率 × 100)、债底防御、正股联动、强制赎回风险预警

  #### 为什么不强行合成一个类？

  因为股票和可转债的定价逻辑与核心指标完全不同：

  • 股票侧重于基本面财报（PE/ROE/净利润）和技术面（均线/成交量）；
  • 可转债侧重于**债券现价（债底防守）与转股溢价率（股性弹幅）**组成的“双低值”。
  将它们分为 DynamicFactorStrategy 和 CBDoubleLowStrategy 两个专门的引擎，代码职责更清晰、运行效率更高。
  ──────
  ### 2. 它们是如何统一在同一个系统里运行的？

  尽管股票策略和可转债策略在计算逻辑上不同，但它们在系统层是 100% 统一的：

  1. 统一的策略基类：
  二者均继承自 BaseStrategy，对外提供完全相同的 generate_signals(date, data) 接口。
  2. 统一的策略工厂 (StrategyRegistry)：
  无论是 DynamicFactorStrategy 还是 CBDoubleLowStrategy，系统在初始化策略时都通过注册器同一管理：
    # 无论传入股票策略还是可转债策略，系统统一调用
    strategy_instance = StrategyRegistry.get(strategy_name, config)

  3. 统一的推荐与持仓引擎 (PortfolioEngine)：
  策略算出来的信号（不管是股票还是可转债）都会统一存入数据库的 recommendations 表。
  PortfolioEngine 内部会自动识别品种（股票 100 股一手加印花税；可转债 10 张一手免印花税），全自动更新资金曲线、持仓和回测。
  ──────
  ### 💡 总结

  • 针对股票：使用配置化的 DynamicFactorStrategy 多因子引擎。
  • 针对可转债：使用专用的 CBDoubleLowStrategy 双低与正股联动引擎。
  • 未来新品种：如果未来要加入 ETF 轮动策略，只需写一个 ETFRotationStrategy 并继承 BaseStrategy，就能完美无缝地融入现在的框架中！

      • 接入成本：低。只需在 update_stock_kline_day.py 的拉取字段列表中补充 pbMRQ, dvRatio 并更新 stock_kline_day 表添加两列即可。
  • PEG (市盈率相对盈利增长比率)：
      • 可行性：使用现有的 peTTM / YOYNI 动态计算即可，无需新增数据表。
  • 毛利率 (Gross Margin) / 净利率 (Net Margin)：
      • 可行性：数据库已有的 stock_profit_quarterly 表中均有记载，在 load_financial_data 的 SQL 中补充提取即可。

  #### 2. 股票技术面维度 (缺：换手率) — 【100% 可支持，即刻可用】

  • 换手率 (Turnover Rate)：

      • 接入成本：极低。可以在计算技术指标时直接提取。

  ──────

  ### 1. 为什么早期会写在同一个 index.html 里面？

  在项目初期，采用 Single-Page Application (SPA，单页应用) 架构把 CSS 样式、页面结构和 JS 控制逻辑放在同一个 HTML 文件中，优点是：

  • 零构建工具依赖：无需 Node.js/Webpack 打包工具编译，凭借 Flask 原生 render 就能快速渲染。
  • 部署极简：Render 云平台部署时不会产生静态资源路径失效或缓存同步问题。
  ──────
  ### 2. 当前遇到的问题（文件过大）

  随着我们给系统增加了 策略编辑模态框、历史回测控制台、每日盘后推演履历表、模拟实盘资金曲线 (Chart.js) 以及刚才新增的动态技术因子，index.html 体积已经增加到了 176 KB / 3,100 行。

  • 可读性与维护性变差：CSS 样式、HTML 布局和 JS 函数混合在一起，排查问题时滚动条拉得很长。
  • 不利于模块化团队协作。
  ──────

> 也就是说 你不建议将策略因子直接存入到数据表中，而是写到json文本中对么？

  是的，我不建议将几十个策略因子拆成几十个独立的数据表列（Column），我极力建议采用“JSON 文本存储 + 后端 Schema 强校验”的做法。

  如果把每一个因子都写成数据库中的独立列，会带来 3 个致命的架构缺陷：
  ──────
  ### 1. 致命缺陷一：数据库频繁结构变迁（Schema Alter Risk）

  • 现状：我们的选股系统正在高速迭代（比如刚才我们新增了 RSI、MACD、布林带、换手率、PB 等近 10 个新因子）。
  • 独立列的代价：如果每个因子都是数据表的一列，每增加或调整 1 个因子，就必须对 TiDB 数据库执行 ALTER TABLE custom_strategies ADD COLUMN enable_rsi TINYINT...。在生产线上，频繁改动数据库表结构是极其危险的操作，极易导致线上服务死锁或崩溃。
  • JSON 的优势：新增 100 个因子，数据库表结构0 变动，灵活性极高。
  ──────
  ### 2. 致命缺陷二：异构资产的“稀疏表”灾难（Sparse Columns）

  • 现状：我们的系统同时支持 股票策略 和 可转债策略。
  • 独立列的代价：
      • 股票策略有 turnover (换手率)、roe、net_profit_yoy 等，但它完全没有可转债的 max_pure_bond_premium (纯债溢价率) 或 min_ytm (到期收益率)。
      • 可转债策略有 ytm、db_low_value 等，但它不需要股票的 volume_surge_factor。
      • 如果把它们全拆成数据表的列，这张表就会充斥着大量的 NULL 垃圾字段（在数据库中称为稀疏列），数据表会变得极其臃肿难维护。

  ──────
  ### 3. 致命缺陷三：无法支持“嵌套层级”与“动态条件组”

  • 策略因子往往是有层级和依赖关系的（例如：stock_linkage 正股联动下嵌套了 ROE 和 PE 范围；tech 下嵌套了短长期均线组合）。
  • 拆成平铺的数据表列，会失去这种天然的嵌套树状结构，导致后端解析逻辑变得极其繁琐。
  ──────
  ### 🏆 结论

  把策略因子存为 JSON 字符串，是目前行业内所有成熟量化平台（如聚宽 JoinQuant、迅投 QMT、优矿等）的通用做法。

  只要我们在后端 Python 层加上严格的格式校验（Schema Validation），就能完美享受 JSON 带来的高扩展性，同时 100% 杜绝脏数据存入数据库！
