  Analyzing Timeout Issue
  经排查，在 Render 部署环境下运行股票选股策略（如 pe_strategy）出现 HTTP 502 (Bad Gateway) 的根源主要由以下 3
  个叠加原因 导致：
  ──────
  ### 1. 🌐 Render 边缘网关 HTTP 100 秒超时限制（HTTP Timeout）

  • 触发过程：前端在控制台点击“开始策略运行”时，向后端发送了同步 HTTP 请求 POST /api/strategies/<stg_id>/run。
  • 原因分析：
      • 后端 server.py 接到请求后，在 Gunicorn 的 Worker 线程中同步执行 run_dynamic_factor_recommendation()。
      • 对于股票策略（如“低估值 PE 策略”），若股票池设为全市场（非沪深 300），系统需要调用 db.py 从 TiDB Cloud
      数据库拉取近 90 天全市场 5000+ 支股票的日 K 线数据（约 30~45 万条 SQL 记录）。
      • 跨网传输海量数据 + Pandas 数据解析 + 均线/PE/ROE 因子计算的总耗时常需 60~120 秒。
      • Render 平台的负载均衡代理（Proxy）对标准 HTTP 同步请求有 100 秒硬性响应超时限制。一旦超过 100 秒未返回
      Response 标头，网关就会直接中断连接并向浏览器返回 502 Bad Gateway。

  ──────
  ### 2. 💥 容器内存溢出导致 Worker 被杀（Render RAM OOM / Worker Restart）

  • 触发过程：Docker 容器内部进程被 Linux 系统强制杀死（SIGKILL），触发 Gunicorn 重新拉起工作进程。
  • 原因分析：
      • Render 免费/入门级实例的内存上限为 512MB。
      • 一次性将全市场 5000 支股票近 90 天的数据拉入内存，并构建 all_data[stock_code] 字典与 DataFrame 对象，在
      Python 解释器中会瞬间产生 300MB~450MB 的峰值内存开销。
      • 加上 Gunicorn + Flask 进程基础内存（约 150MB），总内存极易突破 512MB 限制，触发 Linux 内核的 OOM
      Killer。Gunicorn 主进程捕获到 Worker 挂掉后会打出 Worker exited (code 9) 并重新启动
      Worker，这也直接印证了报错信息中的 “Worker 正在重启”。

  ──────
  ### 3. ⚙️ Web 实时计算 vs 盘后预计算机制偏差

  • 架构逻辑：
      • 系统原设计的架构（参见 GitHub Actions 工作流 update_ashare_data.yml）是每日盘后 18:31 自动拉取行情并执行
      runner.py，把选股结果预先写入数据库 PROJECT_MEMORY.md 表。
      • Web 前端平时查看推荐结果时只需毫秒级查询 SQL SELECT FROM recommendations。
      • 当在 Web 前端手动在线触发策略重新计算时，如果在后台实时进行全量 5000 股的数据重算，便会在资源有限的 Web
      容器内撞上上述的超时与内存墙。

  ──────

  1. 方案 A（轻量优化）：若在 Web 端运行股票策略，针对股票池做 SQL

  ### 🔍 事故根因深度分析 (Root Cause Analysis)

  #### 1. 为什么上一次分批修改后，错误从 502 / OOM 变成了 Failed to fetch？

  • 好消息：上一次我们做的“分批取数与即时
  GC”重构非常成功地解决了内存爆掉（OOM）问题。在最新的日志中可以看到，内存开销一直稳定在 35MB 左右，容器没有再被
  Render 的 512MB 内存机制强制杀死（Status 137）。
  • 核心问题：Failed to fetch 并不是服务器崩溃，而是前端浏览器的 HTTP 同步长连接被网络层/代理网关强行切断（TCP Socket
  Closed）。
      • 当您在 Web 页面点击“开始策略运行”时，前端发出 POST /api/strategies/<id>/run 请求。
      • 目前后端的逻辑是在 HTTP 请求的主线程中，同步、顺序地执行全部 18 个批次的数据拉取与选股计算。
      • Render 部署平台的边缘代理网关（Proxy）对标准同步 HTTP 请求设置了 100 秒的硬性超时断开保护。
      • 在云端跨网环境下，如果 18 个批次的总计算传输时间达到了 105 秒，Render 网关就会强行关掉 TCP
      连接。此时浏览器没有收到任何 HTTP Status Code（哪怕是 502 都没收到），JavaScript fetch() 就会在最底层抛出
      TypeError: Failed to fetch。


  #### 2. 为什么在 5000+ 全量股票模式下，load_financial_data 会拖慢整体计算时间？

  • 在代码中，为了提前加载财报，向 load_financial_data(target_codes=all_stock_codes) 传入了 5200 支股票代码。
  • 这导致后端拼装了一条带有 10,400 个 %s 占位符 的超级 SQL (WHERE p.code IN (%s, %s, ... 10400次 ...)）。
  • 在 TiDB 数据库中，解析并编译包含 1 万个参数的 SQL 会额外浪费 20~30 秒！而全市场四大财报表总共也只有 2
  万多条轻量记录，不传 WHERE IN 直接全量读取仅需 0.5 秒。
  ──────
  ### 💡 针对性解决方案（供您讨论与确认）

  针对上述分析，我建议采用以下 组合优化方案 来彻底解决问题：

  #### 方案一：财报 SQL 拼接优化（缩短计算总耗时）

  • 在 dynamic_factor.py 中，当 target_codes 超过 1000 支（或为全市场）时，不拼装几万个参数的 IN
  语句，直接全量读取财报，将预加载时间从 25 秒缩短至 0.5 秒。

  #### 方案二：策略运行改为异步后台线程处理（彻底根除 HTTP 同步长连接超时）

  • 现状问题：只要代码依然在 HTTP 请求里同步等待 18 个批次算完，一旦哪天云端网络波动导致耗时超过 100
  秒，浏览器必然再次 Failed to fetch。
  • 改造方式：
      1. 用户点击【运行策略】后，后端 server.py 启动一个后台线程（threading.Thread）去异步执行分批计算。
      2. 后端在 0.1 秒内 立即向前端响应返回 {"status": "processing", "message": "策略已在后台启动计算..."}，释放 HTTP
      连接。
      3. 控制台弹窗定时轮询任务状态，算完后提示成功并自动加载最新选股结果。
  • 收益：HTTP 请求 0.1 秒即可完成，彻底摆脱 100 秒超时的物理限制，浏览器再也不会触发 Failed to fetch。
